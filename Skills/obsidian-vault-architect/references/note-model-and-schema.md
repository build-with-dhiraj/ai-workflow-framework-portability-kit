# Note Model & Frontmatter Schema

The structural heart of a durable vault. Two ideas do the heavy lifting: a **layered note model** (sources stay immutable; thinking happens in atomic notes) and a **frontmatter schema** that is the single queryable source of truth.

## The layered note model

Adapted from Andrej Karpathy's "LLM-wiki" pattern and Andy Matuschak's evergreen notes. Four layers, each with one job:

```
raw/        immutable captured sources (transcripts, essays, clips, PDFs-as-md)
atomic/     one idea per note — the RETRIEVAL & REASONING unit
_index.md   one-line summary per atomic note — keeps the corpus LLM-navigable
_moc/       Maps of Content — theme hubs that humans browse
```

### 1. `raw/` — immutable sources
- One note per source (a video transcript, an essay, a talk). **Never edited after capture** — it's the citation anchor.
- Body carries **stable block anchors** so any claim can be cited to an exact location:
  - timestamped media → `^ts-<seconds>` at each segment (`Some sentence. ^ts-742`)
  - prose/essays → `^p-<n>` per paragraph
- Frontmatter records provenance: `source_url`, `published`, `title`, the scope key, and `note_type: raw`.
- Timestamps are *nice to have, not required* — note-level citation to the source URL is a valid floor. Decide by use case; coverage beats precision when forced to choose.

### 2. `atomic/` — the retrieval unit
- **One claim/principle/idea per note.** This is what gets embedded and retrieved. Atomicity is what makes retrieval precise and reasoning composable — a fat "everything about X" note retrieves as mush.
- Each atomic note **cites back** to its raw source: `source_note: "[[raw-note#^ts-742]]"`.
- Evergreen conventions (Matuschak): concept-oriented, densely linked, written as a claim you'd reuse, `status` to track maturity (`draft`→`evergreen`).
- A note's display/byline (if any) must be **derived from its own frontmatter**, never a hardcoded template constant (see anti-patterns — this is a real bug class).

### 3. `_index.md` — the LLM's table of contents
- An auto-generated list of every atomic note as a one-liner. Lets an LLM (or a human) see the whole corpus cheaply and pick what to open. Regenerate on a schedule; never hand-maintain.

### 4. `_moc/` — Maps of Content
- Theme hub notes that link the atomic notes under a topic. This is how humans navigate at scale (the global graph can't — see scale). Generated by cartography, not hand-curated past the first few.

## Frontmatter schema (the queryable contract)

Frontmatter is **the authoritative, machine-queryable truth** — Bases/Dataview read it for dashboards, the retrieval indexer reads it for scoping. One schema, two consumers. Design it once, deliberately.

```yaml
---
# identity & provenance
title: Specific knowledge is found by pursuing your curiosity
note_type: atomic            # raw | atomic | index | moc | persona
source_note: "[[naval-jre-1309#^p-12]]"   # atomic → its raw anchor
source_url: https://...                    # raw only
published: 2019-05-10        # YYYY-MM-DD, ISO-8601 always

# the REQUIRED scope key — drives retrieval isolation AND Bases filtering
mentor: naval-ravikant       # or: source / project / author / domain

# navigation & classification
themes: [leverage, specific-knowledge]     # PLURALIZED key, wikilink-able values
kind: principle              # principle | story | definition | framework | claim
status: draft                # draft | evergreen
---
```

### Schema rules (kepano "file over app" conventions)
- **Pluralize the keys that hold lists** (`themes`, `tags`, `authors`) — singular keys signal a single value and break list queries.
- **`YYYY-MM-DD` everywhere.** ISO dates sort lexically and parse universally.
- **A single required scope key** (`mentor`/`source`/`project`). Every retrieval filter and every per-scope dashboard hangs off it. Missing-scope = orphaned from both systems → make it a lint failure.
- **Composable, flat properties** over nested objects — Bases and most plugins query flat keys best.
- **Link the first mention** of an entity in the body; let the scope/theme keys carry the structured version.
- **Keep frontmatter to identity + classification.** Do NOT store volatile pipeline state here (run timestamps, "indexed: true", processing flags) — that pollutes change-detection and the graph. State belongs in a sidecar (`_system/*.json`), not the note.

## Folder topology

- **Shallow.** ≤3–4 levels. `mentors/<scope>/{raw,atomic}/` + top-level `_moc/`, `_index.md`, `personas/`, `_system/`.
- **Folders are for lifecycle, not taxonomy.** Group by `raw` vs `atomic` vs scope — not by topic. Topic lives in `themes` + MOCs, where it can be many-to-many. Deep topical folder trees are the classic vault that "looks organized" and is impossible to query or relink.
- **One vault, not many.** Cross-vault links don't exist; multiple vaults fragment the graph and the index. Scope with the frontmatter key inside one vault instead.
